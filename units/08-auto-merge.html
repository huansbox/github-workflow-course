auto-merge

「checks 綠了就自動合併」——把等待 CI 的時間還給人。醫生每週合 30 幾個 MR 的秘密之一。

📊 你的數據 你目前的合併都是手動的（handoff-end 甚至把「確認已合併」寫成人工檢查程序）。 auto-merge 是這段流程自動化的第一步：你批准方向，機器等綠燈、按按鈕、刪 branch。 注意你的多數 repo 是 private——本單元會講到 Free 方案在 private repo 上的一個重要限制。

這是什麼

兩種實現方式，適用情境不同：

① 原生 auto-merge（設定即用）

# 前提：repo Settings → General → 勾選 "Allow auto-merge"
gh pr merge 34 --auto --squash --delete-branch

意思是「等這個 PR 的合併條件全部滿足時，自動用 squash 合併」。合併條件來自 branch protection / rulesets（例如 required status checks：CI 必須綠）。 PR 掛上 auto-merge 後，你就可以去做別的事；CI 綠了它自己合。

② Workflow 自製 auto-merge（醫生的做法）

用 Actions 監聽「CI 跑完」事件，在 workflow 裡自行檢查條件後執行 gh pr merge。 醫生的 CCChange repo（每日自動出刊 Claude Code changelog 講義）就是這樣：AI 排程開 PR → CI 綠 → workflow 檢查一串防護條件 → 自動 squash 合併 → 觸發部署。適合需要自訂條件 （誰開的 PR？改了哪些檔案？）的無人值守流程。

醫生的防護清單（無人值守的教科書）

他的 auto-merge workflow 在合併前檢查五件事，每一條都值得抄：

檢查為什麼
PR 不是來自 forkfork PR 等於陌生人的程式碼；自動合併它 = 把 repo 送人。
不是 draft、base 是 maindraft 是「還沒好」的明示；合錯目標 branch 的事故不該由自動化放大。
作者是擁有者/協作者（API 查證，不信 PR 內容）判斷依據一律來自 GitHub API 的事實，不來自 PR 自己聲稱的任何東西。
必須掛特定 label（如 claude-daily）label 是人為的「准許自動合併」開關——沒掛的 PR 永遠留給人審。
改動只限內容目錄（如 src/content/）動到 workflow、build script 的 PR 一律要人看——否則 AI（或攻擊者）可以改掉檢查它自己的規則。

另外還有一條時序防護：合併前重新讀取當下的 check 狀態，而不是相信事件發生當時的快照—— 事件與合併之間，別的檢查可能已經轉紅。

常見的坑

  • 沒有任何 required checks 時，--auto 立刻合併：auto-merge 的語意是「等條件滿足」；條件是空集合就是「現在」。想要「等 CI 綠」，CI 必須被設為 required status check，否則 CI 紅著照樣合。
  • Free 方案的 private repo 不能設 branch protection / rulesets 的強制規則：這對你直接相關——你的 repo 大多 private。三條路：(a) 該 repo 夠重要就轉 public 或升級 Pro；(b) 用醫生的 workflow 自製法（不依賴 branch protection，Actions 在 private repo 免費額度內可用）；(c) 維持手動合併。
  • 把「檢查 CI」寫成查 commit status API：GitHub 有新舊兩套回報機制——Actions 的結果在 check runs API；舊的 combined status API 對「只有 Actions 檢查」的 commit 會回報 pending/0 checks，讓你的守門邏輯變成永遠放行或永遠卡住。醫生的 workflow 註解特別標了這個坑。
  • 自動化迴圈：自動合併 → 觸發部署 → 部署 commit 又觸發……第 10 單元會講 GitHub 的抑制機制與正確的接力方式。
💡 給你的優化建議 你的 handoff-end「完成路徑」目前是：確認合併 → 切回 main → 刪 branch，全手動。 導入方式（漸進）：先在一個 public repo（如 aiden-study）開 "Allow auto-merge" + 把 CI 設 required， 流程改成「開 PR 後掛 gh pr merge --auto --squash --delete-branch」—— handoff-end 那套「比較變更確認已合併」的檢查依然照跑，只是合併本身不再等你。

✅ Takeaways

  • 原生 auto-merge = 「條件滿足時自動合併」；條件來自 branch protection 的 required checks。
  • 沒有 required checks，--auto 就是立刻合併——CI 紅綠與它無關。
  • Free 方案 private repo 無法強制 branch protection；替代方案是 workflow 自製 auto-merge。
  • 無人值守的防護：拒 fork、拒 draft、驗作者、要 label、限檔案路徑、合併前重讀 check 狀態。
  • 判斷依據永遠來自 API 事實，不來自 PR 自己聲稱的內容。
