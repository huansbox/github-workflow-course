issue

Issue 不只是「回報問題」——它是待辦事項、規格書、審核點，以及自動化的觸發器。

📊 你的數據 gh issue 出現 1211 次——你已經在用 issue 當 tracker，你的 to-issues skill 更是把 issue 當規格書 （What to build + acceptance criteria checkboxes）。這一單元補的是你可能還沒用滿的部分： closing keywords、label 驅動自動化、issue template，以及 gh issue edit --body 的整體覆蓋陷阱—— 你的 skill 裡那套 read→modify→verify 流程，正是為了這個陷阱存在的。

這是什麼

一則 issue = 標題 + Markdown body + 討論串 + 一組 metadata（label、assignee、milestone、關聯 PR）。 醫生的用法把它的三重身分用滿：

  • 待辦事項：開 issue = 收工作；關 issue = 完工。清單即 backlog。
  • 審核點：「它分析問題完，我在 issue 上看他的計畫，批准」——AI 把計畫貼在 issue 留言，人只做批准。
  • 自動化觸發器：他的 vox-styled-reels repo 裡，對 issue 貼上 card label 就會觸發 workflow 把 issue 內容轉成影片卡片再開 PR（第 10 單元會拆解這個機制）。

怎麼用

指令面

gh issue create --title "..." --body-file spec.md --label bug
gh issue list --state open --label bug
gh issue view 12 --comments
gh issue comment 12 --body "進度：..."
gh issue close 12 --comment "完成，見 PR #34"
gh issue edit 12 --add-label blocked

Body 裡的兵器

  • Task list：- [ ] 條目。GitHub 會在 issue 列表顯示完成度（3/5），你的 acceptance criteria 就是這個。
  • Closing keywords：PR 描述寫 Closes #12（或 fixes / resolves），PR 合併進 default branch 時自動關掉 issue。這是 issue 與 PR 之間最重要的一條線。
  • 引用：任何留言寫 #12 會建立雙向連結；commit message 寫 #12 也會出現在 issue 的時間軸上。
  • Sub-issues：issue 可以掛子 issue 形成父子階層（你的 to-spec → child issues 結構可以直接用上）。task list 是輕量版；子項需要各自的討論串與狀態時才升級成 sub-issue。

Issue template

在 repo 放 .github/ISSUE_TEMPLATE/task.md（或 .yml 表單版），開 issue 時自動套格式。 對你的實際意義：to-issues 的 Issue template（What to build / Acceptance criteria / Testing decisions…）可以做成 repo 的 issue template，讓人手開的 issue 和 AI 發布的 issue 長一樣。

常見的坑

  • gh issue edit --body 是整體覆蓋：gh 沒有「只改一行」的 API——要勾一個 checkbox，就得讀出全文、改那一行、整包寫回。中間若有人動過 body，你會把對方的修改輾掉。你的 handoff-end 為此規定了「讀→只改該行→byte 比對→送出前再讀一次」，這不是儀式，是這個 API 形狀逼出來的。
  • Closing keywords 只在合併進 default branch 時生效：merge 到其他 branch 不會關 issue；直接 push（不走 PR）時 commit message 裡的 fixes #12 也會關——有時是驚喜，有時是事故。
  • 寫成小說的 issue：body 塞滿討論過程，後來的人分不清哪句是結論。你的 skill 的作法是對的：body 只放規格與驗收，進度與討論放留言。
  • tracker 寫入權限：能讀、能 clone 一個 repo 不代表該把工作項寫進人家的 tracker。你的 CLAUDE.md 已把這條列為授權規則。
💡 給你的優化建議
  1. 把 to-issues 的模板做成 .github/ISSUE_TEMPLATE/，人工開單也走同一格式。
  2. PR 一律寫 Closes #N，讓「merge 自動關 issue」取代手動收尾——這是醫生流程裡「完成就是 PR」的機械保證。
  3. 用 label 表達狀態機（如 needs-review / blocked / claude-approved），之後第 10 單元你會看到 label 可以直接當 workflow 的觸發條件。

✅ Takeaways

  • Issue 的三重身分：待辦、規格與審核點、自動化觸發器。
  • PR 描述寫 Closes #N，合併進 default branch 時自動關 issue。
  • task list 給輕量子項；需要獨立討論串時才用 sub-issue。
  • gh issue edit --body 永遠是整包覆蓋——併發修改要靠讀回比對防守。
  • body 放規格與驗收，進度放留言；別把 issue 寫成小說。
