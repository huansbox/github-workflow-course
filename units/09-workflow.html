workflow

GitHub Actions 的解剖課：一個 YAML 檔怎麼變成雲端幫你跑的機器人。

📊 你的數據 gh workflow 59 次、actions/checkout 15 次——這裡就是你統計上最大的空白。 但你其實已經有一個 Actions workflow 在身邊：repo-wiki skill 的 publish-wiki.yml。 這一課給你解剖工具，讓你能讀懂並改造任何 workflow——包括這個課程 repo 自己的 deploy.yml。

五個名詞，一張圖

Event（事件：push、PR、排程……）
  └─ 觸發 Workflow（.github/workflows/*.yml，一檔一個）
       └─ 包含一或多個 Job（各自在一台全新的 Runner 虛擬機上跑，預設互相平行）
            └─ 包含一串 Step（依序執行；shell 指令或現成的 Action）
                 └─ Action（別人打包好的可重用步驟，uses: 引入）
  • Workflow：放在 repo 的 .github/workflows/ 下的 YAML 檔。
  • Runner：GitHub 提供的拋棄式虛擬機（ubuntu-latest 最常用）。每個 job 開機時是空的——連你的 repo 都沒有，所以幾乎每個 job 第一步都是 actions/checkout。
  • Step 兩型：run: 跑 shell 指令；uses: 引入現成 Action（Marketplace 上數萬個）。

逐行讀一個真的 workflow

這是本課程 repo 自己的 .github/workflows/deploy.yml（把靜態網站部署到 GitHub Pages）：

name: Deploy to GitHub Pages     # 顯示在 Actions 頁籤的名字

on:                              # ── 何時觸發（第 10 單元詳講）
  push:
    branches: [main]             # main 有 push 就跑
  workflow_dispatch:             # 也允許手動按按鈕跑

permissions:                     # ── 這個 workflow 的 token 權限（第 11 單元詳講）
  contents: read                 # 只需要讀 repo
  pages: write                   # 寫 Pages
  id-token: write                # Pages 部署的身分驗證

concurrency:                     # ── 同時只跑一個部署
  group: pages
  cancel-in-progress: false      # 進行中的不取消（取消部署會留下半套狀態）

jobs:
  deploy:
    runs-on: ubuntu-latest       # 跑在哪種 runner
    timeout-minutes: 10          # 保險絲：卡住不會吃光額度
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}   # 表達式語法：引用其他 step 的輸出
    steps:
      - uses: actions/checkout@v5            # 第一步幾乎永遠是拿到 repo
      - uses: actions/configure-pages@v5     # 官方 Pages 設定 action
      - uses: actions/upload-pages-artifact@v4
        with:                                # with: 是傳給 action 的參數
          path: .                            # 整個 repo 就是網站（零 build）
      - id: deployment
        uses: actions/deploy-pages@v4

讀懂這一個，你就讀得懂八成的 workflow：醫生的 CCChange deploy.yml 結構完全相同， 只是中間多了 pnpm install、pnpm build 幾個 run: step。

幾個馬上會用到的細節

  • 多 job 預設平行；要串行用 needs:（如 deploy: needs: build）。job 之間不共享檔案系統——傳檔案要用 artifact。
  • Action 要釘版本：@v5（大版 tag，一般夠用）或 @<完整 SHA>（供應鏈最嚴格）。不寫版本或用 @main = 讓別人隨時改變你 CI 裡跑的程式碼。
  • 費用：public repo 的 Actions 免費無上限；private repo Free 方案每月 2000 分鐘免費（Linux runner 計 1x）。你的 private repo 做輕量 CI 綽綽有餘。
  • timeout-minutes 是好習慣：預設 6 小時——一個卡死的 job 可以默默吃掉你半天的免費額度。

常見的坑

  • YAML 縮排：兩格縮排、冒號後要空格；on:、jobs: 層級錯一格就整檔失效。找不到 workflow 時先檢查縮排與檔案路徑（必須是 .github/workflows/，不是 .github/workflow/）。
  • runner 是空機器：忘了 checkout，後面的步驟會在空目錄裡執行然後報 file not found——新手第一坑。
  • 某些觸發只認 default branch 上的 workflow 檔：schedule、workflow_dispatch 等要等 workflow 檔合進 main 才生效——在 branch 上開發新 workflow 時「怎麼按不了手動執行」多半是這個原因。
  • 把 workflow 當本機腳本除錯：每改一行 push 一次等雲端跑，迭代極慢。先把邏輯寫成本機可跑的 script（repo 裡的 scripts/），workflow 只負責「在對的時機呼叫它」——這也讓 script 可以被本機測試。

✅ Takeaways

  • 層級：Event → Workflow → Job（平行、各自一台空 VM）→ Step（run: 或 uses:）。
  • 幾乎每個 job 第一步是 actions/checkout——runner 開機時什麼都沒有。
  • Action 一律釘版本（@v5 起步）；timeout-minutes 一律設。
  • public repo Actions 免費；private repo Free 方案每月 2000 分鐘。
  • 邏輯寫在可本機執行的 script，workflow 只做時機與膠水。
