pull-request

PR 不是「請求合併」的表單，是一個掛在 branch 上的審核介面：diff、討論、檢查結果、證據截圖都收在這裡。

📊 你的數據 「pull request」在你的紀錄出現 2468 次，但 gh pr 只有 361 次——你談論 PR 多、用指令操作 PR 少。 你的 issue 完成協議要求「clean-context code review」；這單元要說的是：GitHub 的 PR review 介面 就是為這件事設計的原生載體，而 gh pr 能讓整個流程不離開終端機。

這是什麼

PR 的本體是「兩個 branch 之間的差異 + 圍繞這個差異的一切」：

  • diff：base（通常 main）與 head（工作 branch）的差異。PR 跟著 branch 走——PR 開著時再 push 新 commit，會自動進同一個 PR。
  • 描述：做了什麼、為什麼、怎麼驗證、Closes #N。
  • review：逐行留言 + 三種結論（Approve / Request changes / Comment）。
  • checks：CI workflow 的紅綠燈直接顯示在 PR 上（第 12 單元）。
  • 附件：描述與留言可以貼圖。醫生的技巧：「UI 視覺的東西請 AI 用 playwright 截圖加在 MR note 裡」——把肉眼驗證的證據固定在審核紀錄上。

何時用

  • Draft PR：工作還沒完成但想讓 CI 先跑、或想讓人先看方向時，開 draft。draft 不能被合併，也不會請求 review。完成後按 Ready for review（或 gh pr ready）。
  • 自己審自己的 PR：單人 repo 沒有第二個人，但 PR 仍有價值——它強迫你在合併前用 diff 視角重看一次變更，而且 GitHub 不允許 approve 自己的 PR，所以單人流程的「批准」就是合併動作本身。你的 clean-context review（開一個乾淨 context 的 AI 當審查者）正好補上「第二雙眼睛」的缺。

怎麼用

# 開 PR（--fill 用 commit message 當標題與描述）
gh pr create --fill --body "Closes #12"
gh pr create --draft --title "WIP: 重構驗證層"

# 看與審
gh pr list
gh pr view 34 --comments        # 描述與討論
gh pr diff 34                   # 終端機看 diff
gh pr checks 34                 # CI 紅綠燈
gh pr checkout 34               # 把 PR 的 branch 抓到本地跑跑看

# review 動作
gh pr review 34 --approve
gh pr review 34 --request-changes --body "邊界條件沒處理"
gh pr comment 34 --body "截圖如下 ..."

# 收尾
gh pr ready 34                  # draft → ready
gh pr merge 34 --squash --delete-branch

常見的坑

  • PR 是 branch 對 branch，不是 commit 對 commit：合併前又 push 了「順手改」，它就進了同一個 PR。要嘛忍住，要嘛另開 branch。
  • review 中 force-push：rebase 後 force-push 會改寫 PR 的 commit 歷史，審查者原本留言的行可能對不上、已讀的 commit 標記失效。單人無所謂；有審查者時，review 期間用普通 commit 補，合併時再 squash。
  • 描述空白的 PR：--fill 至少把 commit message 帶進去。描述是給「三個月後的自己」和 changelog 生成器（第 7 單元）讀的——squash 合併時 PR 標題會成為 main 上的 commit message，寫爛標題等於寫爛歷史。
  • 用 PR 留言當聊天室：與這個 diff 無關的討論回 issue 去。PR 關掉後留言很少有人再翻。
💡 給你的優化建議 你已裝了 playwright 工具。UI 類變更可以把「render → 截圖 → 貼進 PR」變成慣例： gh pr comment 34 --body "..." 本身不能附檔，但描述與留言支援 Markdown 圖片——把截圖 commit 進 repo 或貼上傳連結即可。 更省事的做法是請 Claude 在 PR 描述生成時直接附上驗證截圖，讓「看 PR」一眼分辨動了什麼。

✅ Takeaways

  • PR 跟著 branch 走：開著的 PR 會吸收該 branch 之後所有 push。
  • Draft PR 讓 CI 先跑、方向先看，且防止被誤合併。
  • review 三結論：Approve / Request changes / Comment；不能 approve 自己的 PR。
  • squash 合併時 PR 標題就是 main 的 commit message——標題品質＝歷史品質。
  • 把驗證證據（測試輸出、截圖）固定在 PR 上，審核才有對象。
