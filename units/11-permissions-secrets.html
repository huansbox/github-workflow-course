permissions-secrets

workflow 是替你持有權限跑程式的機器人。這一課講它的鑰匙從哪來、能開哪些門、以及怎麼不讓別人偷走。

📊 你的數據 GITHUB_TOKEN 在你的紀錄只出現 12 次。你開始寫 workflow 之後， 這一課的內容就是「出事時最貴」的知識——權限給錯不會馬上爆炸，它只是安靜地等一個惡意 PR。

GITHUB_TOKEN：自動核發的鑰匙

  • 每次 workflow run 開始時，GitHub 自動核發一個只在這次 run 有效的 token（secrets.GITHUB_TOKEN），run 結束即失效。用它呼叫 API、push、開 PR，都不需要你自己造 token。
  • 它能開哪些門由 permissions: 區塊決定： 
    permissions:
  contents: read        # 讀 repo（checkout 需要）
  pull-requests: write  # 開/合 PR、留言
  issues: write         # 開/關 issue
  actions: write        # dispatch 其他 workflow
  • 最小權限原則：workflow 檔裡明寫 permissions:，只給用得到的。repo Settings → Actions 還能把預設值改成 read-only（建議），逼每個 workflow 顯式申請寫入權。
  • GITHUB_TOKEN 出不了本 repo。要跨 repo 操作（push 到別的 repo、觸發別 repo 的 workflow）才需要 PAT（personal access token）——用 fine-grained PAT、限定 repo 與權限、放進 secrets。

Secrets：自備的鑰匙

# 設定（或用網頁 Settings → Secrets and variables → Actions）
gh secret set ANTHROPIC_API_KEY

# workflow 裡使用
steps:
  - run: python sync.py
    env:
      API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
  • 存進去就讀不回來（只能覆蓋或刪除）；log 裡出現 secret 值會被自動遮罩成 ***。
  • 非機密的設定值用 vars.（Variables）——看得見、好除錯；secrets 只放真正的機密。

Fork PR：攻擊面在這裡

public repo 收到 fork 的 PR 時，pull_request 觸發的 workflow 會跑PR 的程式碼—— 如果這時 secrets 也給它、token 又有寫入權，任何路人開個 PR 就能偷走你的鑰匙。所以 GitHub 的預設防護是：

  • fork PR 的 pull_request run：拿不到 secrets，GITHUB_TOKEN 降為唯讀。
  • 危險的是 pull_request_target：它以 base branch 的身分跑（有 secrets、有寫入權）。它存在的正當用途是「只讀 PR 的 metadata 做 label/留言」；一旦在裡面 checkout 了 PR 的程式碼又執行它（安裝依賴、跑 build 都算執行），就是教科書級漏洞——這類事故有個名字叫 pwn request。
  • 醫生 auto-merge 的第一條防護「拒絕 fork PR」就是這個攻擊面的應對：無人值守的寫入權限流程，乾脆不對外部程式碼開放。

常見的坑

  • permissions 不寫，吃到過寬的預設：舊 repo 的預設可能是全項 write。習慣：每個 workflow 都明寫，從 contents: read 開始按需求加。
  • 遮罩不是加密：log 遮罩擋直接輸出，擋不住 echo ${KEY:0:4} 分段洩漏、寫進 artifact、或傳給第三方 action。secret 只交給信任的（釘了版本的）程式碼。
  • 私 repo 的 secrets 也不是保險箱：任何能改 workflow 檔的人都能寫程式把 secret 送出去。secrets 的信任邊界=有寫入權的人的集合。
  • 用 PAT 當萬靈丹：PAT 權限通常遠大於需求、不會自動過期輪替。GITHUB_TOKEN 夠用就不要 PAT；要用就用 fine-grained + 最小範圍。
  • token 掉進 URL 或 log：你的 repo-wiki skill 已有這條鐵律——token 不進 URL、不進 process arguments，一律走 credential helper。同一原則適用於 workflow。

✅ Takeaways

  • GITHUB_TOKEN 每 run 自動核發、run 完失效、出不了本 repo；權限由 permissions: 控制。
  • 每個 workflow 明寫最小 permissions:；repo 預設調成 read-only。
  • fork PR 拿不到 secrets 是預設防護；pull_request_target + checkout PR 程式碼 = pwn request 漏洞。
  • 遮罩不是加密：secret 只交給信任且釘版的程式碼。
  • 機密放 secrets、設定放 vars；跨 repo 才考慮 fine-grained PAT。
