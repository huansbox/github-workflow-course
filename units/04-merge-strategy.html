merge-strategy

合併 PR 的三種姿勢——merge commit、squash、rebase——決定 main 的歷史長什麼樣，也決定你刪 branch 時會不會被 Git 嚇一跳。

📊 你的數據 你的 handoff-end skill 裡有一段很特別的規定：「squash 或 rebase 合併會讓工作以新 commit 落地、舊 tip 變成不可達， 所以要比較 changes 而非 commit identity，且 git branch -d 會拒刪，要憑證據 fallback 到 -D」。 這段文字就是本單元的核心考點——你（或幫你寫 skill 的 AI）顯然踩過這個坑。這一課把「為什麼」補齊。

三種合併

假設 PR 是 feature（3 個 commit：A、B、C）合進 main：

方式main 上留下什麼特性
Merge commit
gh pr merge --merge		 A、B、C 原樣進入，外加一個 merge commit M 歷史完整保留、可看出「這三個 commit 是一批的」；但 main 歷史會有大量分叉線。A、B、C 的 hash 不變——branch tip 仍可達。
Squash
gh pr merge --squash		 壓成一個全新 commit S（message 取自 PR 標題） main 歷史一 PR 一 commit，極乾淨；工作過程的零碎 commit 消失。S 是新 hash——原 branch tip 從 main 看是不可達的。
Rebase merge
gh pr merge --rebase		 A′、B′、C′（逐一重放的新 commit）線性接上 保留逐步歷史又沒有 merge commit；但 A′≠A——同樣是新 hash，原 tip 一樣不可達。

何時用哪個

  • 單人 + AI 協作的 repo：squash 是最佳預設。工作 branch 上的 commit 常是「WIP」「fix」「再修一下」，沒有保留價值；squash 讓 main 讀起來就是 changelog。醫生的 auto-merge 用的正是 --squash --delete-branch。
  • merge commit：當 branch 上的每個 commit 都是精心整理的邏輯單元（例如一個大重構分五步，每步可獨立理解），值得整批保留時。
  • rebase merge：想要線性歷史又想保留逐步 commit。實務上最少用——要嘛過程沒價值（squash），要嘛想標記批次（merge commit）。
  • repo 可以在 Settings 裡限制允許的合併方式，強迫一致性；也可開 Automatically delete head branches，合併後自動刪遠端 branch。

常見的坑

  • squash/rebase 後 git branch -d 拒刪：-d 的安全檢查是「這個 branch 的 commit 是否可達（已被包含）」。squash 後 main 上是新 commit S，原本的 A、B、C 不在任何地方——Git 認為「工作會遺失」而拒絕。但變更內容其實已經在 main 裡了。正確處置：比較變更而非 commit（例如 git diff main...feature 為空、或 PR 顯示 merged），確認後用 -D 強刪。你的 handoff-end 寫的就是這套。
  • 用 PR 狀態當唯一證據：PR 顯示 merged 不代表本地 main 已更新，也不代表 branch 上沒有合併後又多出的 commit。刪之前 git fetch --prune + 再確認一次。
  • squash 大 PR：一個 800 行的 PR squash 成一個 commit，日後 git bisect / git blame 的解析度就是這 800 行。這不是 squash 的錯，是 PR 太大的錯——變更切小，squash 才無損。
  • 混用策略讓歷史難讀：同 repo 有時 squash 有時 merge commit，歷史裡分叉與線性混雜。選一個當預設，例外要有理由。
💡 給你的優化建議 在你的 repo 開兩個設定就能省掉 handoff-end 的一部分手工： Settings → General → Pull Requests → 只允許 squash + 勾 Automatically delete head branches。 遠端 branch 由 GitHub 自動清，本地那份仍要照 skill 的證據流程刪（git fetch --prune 後 -D）。

✅ Takeaways

  • merge commit 保留原 commit（hash 不變）；squash 與 rebase merge 都產生新 commit，原 branch tip 變不可達。
  • 單人 + AI 流程的預設選 squash：main 一 PR 一 commit，PR 標題即歷史。
  • squash 後 branch -d 拒刪是預期行為——比較變更（git diff main...branch）確認後用 -D。
  • 刪 branch 前先 git fetch --prune，別只看 PR 狀態。
  • repo 設定可限制合併方式並自動刪 head branch。
