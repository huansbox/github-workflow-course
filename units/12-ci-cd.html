ci-cd

最後一課：把前面 11 個單字組裝成醫生那條「沒了，毫無技巧，全是感情」的流水線。

📊 你的數據 gh run 154 次——你偶爾看過 run 結果，但還沒有一條屬於自己的流水線。 這一課結束時，你會知道每一節車廂是哪個單元教的，以及第一條流水線該從你的哪個 repo 開始。

兩個縮寫的實務意義

  • CI（Continuous Integration）：每個 PR 自動跑檢查（lint、test、build），在合併前擋住壞變更。CI 的產出是紅綠燈。
  • CD（Continuous Deployment）：merge 進 main 後自動部署/發布，在合併後把 main 變成現實。CD 的產出是上線的東西。
  • 一句話：CI 守門，CD 送貨。掛的觸發事件不同（pull_request vs push: main），需要的權限不同（read vs write），這就是為什麼它們通常是兩個 workflow 檔。

醫生的完整流水線（每節車廂的出處）

Issue（待辦＋計畫審核）..................... 單元 02
  → Claude 開 branch 寫 code、開 PR ........ 單元 01、03
  → CI 檢查（pull_request 觸發）............ 單元 09、10
  → 人看 PR：diff、截圖、可疑之處 .......... 單元 03
  → auto-merge（綠燈＋防護清單→squash）..... 單元 04、08
  → deploy（push main 觸發；dispatch 接力）.. 單元 10
  → release + changelog（自動上版 Beta）..... 單元 06、07
  → schedule（每日 cron 定期任務）.......... 單元 10

注意這條線上人只出現兩次：批准 issue 上的計畫、看 PR。其餘全是機器。 這就是「一天合 30 幾個 MR」的容量從哪來——人的時間只花在判斷，不花在搬運。

組裝時的三個實務工具

① concurrency：同類 run 不互撞

# CI：新 push 讓舊 run 失去意義 → 取消它，省時間省額度
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

# 部署：取消進行中的部署會留下半套狀態 → 排隊不取消
concurrency:
  group: pages
  cancel-in-progress: false

同一個設定，CI 和部署的正確值相反——照抄別人的 concurrency 前先想這一層。

② matrix：一份定義，多份執行

strategy:
  matrix:
    python: ["3.11", "3.12", "3.13"]
steps:
  - uses: actions/setup-python@v5
    with:
      python-version: ${{ matrix.python }}

一個 job 定義展開成三個平行 job。醫生的 release-cards 用它「一張卡一台 runner」平行渲染影片。

③ 除錯迴路：gh run

gh run list --workflow=ci.yml     # 最近的 run
gh run watch                      # 即時盯著跑
gh run view 12345 --log-failed    # 只看失敗 step 的 log（最常用）
gh run rerun 12345 --failed       # 只重跑失敗的 job

常見的坑

  • CI 綠 ≠ 沒問題：CI 只驗證你寫了的檢查。測試薄弱的 repo，綠燈只代表「沒有壞得很明顯」。auto-merge 的信心上限=測試的信心上限——要無人值守，先投資測試。
  • 部署 workflow 用 cancel-in-progress: true：新 push 取消進行中的部署，網站可能停在半新不舊的狀態。CCChange 的註解特別寫了這條。
  • 在 CI 裡重現不了本機沒有的失敗：環境差異（時區、locale、檔案大小寫——macOS 不分大小寫、Linux 分！）是常客。你在 mac/Windows 之間切換開發，Linux runner 是第三個環境。
  • 一開始就想全自動：醫生的流水線是長出來的，不是一天蓋好的。順序建議：先 CI（最便宜、立刻有感）→ 手動合併一陣子觀察 CI 可信度 → auto-merge → CD。
💡 你的第一條流水線（具體建議）
  1. CI 起手式：挑 strava-sync（Python、有排程需求的真專案）加一個 ci.yml：pull_request 觸發，跑 uv run pytest 與 lint。
  2. cron 起手式：它如果有「定期同步」需求，schedule + workflow_dispatch 正是教科書場景（secrets 放 API 金鑰，第 11 單元）。
  3. CD 起手式：本課程 repo 的 deploy.yml 已經是一個可抄的 Pages 部署範本。
  4. 之後每個新 repo 開場就帶 ci.yml——讓「PR 必有紅綠燈」成為你的 handoff 流程的機器版底線。

✅ Takeaways

  • CI 守門（pull_request、read 權限）、CD 送貨（push main、write 權限）——兩個檔各司其職。
  • concurrency：CI 取消舊 run、部署排隊不取消——方向相反。
  • matrix 把一份 job 定義展開成多份平行執行。
  • 除錯三連：gh run list → view --log-failed → rerun --failed。
  • 導入順序：CI → 觀察 → auto-merge → CD；auto-merge 的信心上限是測試的信心上限。
