github-flow

一條永遠可部署的 main、短命的工作 branch、PR 合併、merge 觸發自動化——四句話就是整套心法。

📊 你的數據 你每天在走這個循環的前半段：commit（7068）、push（4199）、branch（2388）、PR（2329）都是高頻詞。 你的 handoff-end skill 甚至把「確認 branch 已合併 → 刪 branch」寫成了標準程序。 缺的是循環的最後一步：merge 之後自動發生的事——那是第 3 章的主題。

這是什麼

GitHub Flow 是 GitHub 官方推的最簡分支模型，整個循環只有六步：

Issue（要做什麼）
  → git switch -c 工作branch（從 main 切出）
  → commit + push（小步前進）
  → Pull Request（提出合併，掛審核）
  → Merge（進 main，刪 branch）
  → 自動化（CI/CD 部署、changelog、通知……）

核心約定只有一條：main 上的每個 commit 都必須是可部署的狀態。 所有還不能部署的半成品都活在 branch 上；branch 的壽命以「一個 PR」為單位，合併即死。

對照另一個常聽到的 Git Flow（有 develop、release、hotfix 等長期分支）： Git Flow 是為「一次發一個版、多版本並行維護」的軟體設計的（例如桌面軟體 v2.3 與 v3.0 同時要修 bug）。 持續部署的網站、單人專案用它只會多出一堆要同步的分支。醫生那句「小至收發 Line 大到醫院系統全部一貫」， 用的正是 GitHub Flow 而不是 Git Flow——因為他的東西 merge 完就直接上線。

何時用

  • 用 GitHub Flow：持續部署的服務、個人專案、需要留審核紀錄的工作——也就是你幾乎所有的 repo。
  • 不必開 branch：你的版控規範已經寫了——「可在目前 session 完整交付、不需 issue 或獨立 review 的低風險修改，可在 main 完成」。這與 GitHub Flow 不衝突：main 可部署的前提下，小改直接上是務實的化簡。
  • 該開 branch 的訊號：做不完要跨 session、需要 review、或改壞會影響已上線的東西。你的 handoff-end 第一條規則就是這個判斷。

怎麼用

# 從 issue 出發（醫生：「Issue 就是待辦事項」）
gh issue view 12

# 切出工作 branch（命名帶 issue 編號，之後好追）
git switch -c 12-fix-login

# 小步 commit、push 上去
git push -u origin 12-fix-login

# 開 PR，描述裡寫 Closes #12（合併時自動關 issue）
gh pr create --fill --body "Closes #12"

# 審核通過後合併＋刪 branch
gh pr merge --squash --delete-branch

常見的坑

  • 長壽 branch：branch 活越久，和 main 的距離越遠，合併衝突越痛。解法不是「更會解衝突」，而是把工作切小、快合快刪。你的 to-issues skill 把工作切成「thin, independently verifiable slices」就是在源頭防這個坑。
  • main 上留著壞掉的 commit：一旦允許「main 暫時是壞的」，整套自動化（merge 即部署）就不能信任。CI 檢查（第 12 單元）就是用機器守住這條線。
  • 把 branch 當長期儲存：合併後不刪 branch，列表會長滿殭屍。branch 只是 PR 的載體，歷史都在 main 和 PR 紀錄裡。
  • 循環走半套：有 branch 有 PR，但 merge 後的部署、changelog 還是手動——這是你目前的狀態。自動化補上之前，PR 只是「比較安全的手動流程」；補上之後才是完整的 GitHub Flow。

✅ Takeaways

  • GitHub Flow = main 永遠可部署 + 短命 branch + PR 合併 + merge 觸發自動化。
  • Git Flow 是多版本並行的模型；持續部署與單人專案用 GitHub Flow 就夠。
  • branch 壽命以一個 PR 為單位，合併即刪。
  • 低風險小改直接進 main 不算犯規，前提是 main 保持可部署。
  • 你已會前半套；這門課的重點是補「merge 之後自動發生的事」。
