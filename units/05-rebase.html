rebase

把你的 commit 抱起來，放到另一個基底上重放一次。歷史因此變直，但 commit 也因此換了身分證。

📊 你的數據 git rebase 229 次 vs git merge 547 次——rebase 是你的低頻工具。 好消息：你的流程（squash 合併 PR）已經覆蓋了 interactive rebase 最大的用途（整理零碎 commit）。 所以這一課的重點放在兩個仍然值得會的場景：PR 前同步 main、force-with-lease 的安全網， 以及那條不可違反的金律。

這是什麼

git rebase main 在做三件事：找出你 branch 上 main 沒有的 commit → 暫存起來 → 把 branch 指到 main 最新端點，逐一重放。結果是線性歷史，代價是每個重放的 commit 都是新 hash （parent 變了，hash 必變）。

rebase 前：            rebase 後：
      A---B  (feature)              A'--B'  (feature)
     /                             /
D---E---F  (main)         D---E---F  (main)

對比 merge：git merge main（在 feature 上）會產生一個合併 commit，歷史分叉但 commit 不變。 兩者達成同一件事——讓 branch 拿到 main 的最新變更——差別只在歷史形狀與 hash 是否改寫。

何時用

  • PR 前同步 main：branch 開發到一半 main 前進了，rebase 讓你的 PR diff 乾淨地建立在最新 main 上，而不是混著一個「Merge branch 'main' into …」的合併 commit。
  • git pull --rebase：同一條 branch 在兩台機器間輪流工作時（你的 mac/Windows 切換！），pull --rebase 把本地未推的 commit 重放到遠端最新之上，避免每次 pull 都長出無意義的合併 commit。可設 git config pull.rebase true 當預設。
  • Interactive rebase（git rebase -i）：送審前整理 commit——squash（併入前一個）、fixup（併入且丟棄 message）、reword（改 message）、drop（刪除）、edit（停下來改內容）。若你的 repo 一律 squash 合併，這件事 GitHub 會在合併時幫你做，需求就小很多。注意：Claude Code 環境不支援互動式指令，rebase -i 要自己在終端機開編輯器操作。

怎麼用

# 把 feature 重放到最新 main 上
git switch feature
git fetch origin
git rebase origin/main        # 衝突時：解掉 → git add → git rebase --continue
git rebase --abort            # 隨時放棄，回到 rebase 前

# rebase 過的 branch 推回遠端（歷史已改寫，普通 push 會被拒）
git push --force-with-lease   # 不要用 --force

# 兩台機器同步同一條 branch
git pull --rebase

常見的坑

  • 金律：別 rebase 別人已經拿到的 commit。rebase 改寫 hash——如果同事（或另一台機器、或一個開著的 PR 的審查者）手上有舊 hash，他們的歷史和你的從此對不上，修復既麻煩又容易出錯。自己一個人用的 branch 隨便 rebase；推出去且有人依賴之後就不要。
  • --force vs --force-with-lease：force 無條件覆蓋遠端——如果另一台機器剛 push 了新 commit，force 會把它抹掉。force-with-lease 檢查「遠端還是我上次看到的樣子」才覆蓋，等於樂觀鎖。永遠用後者。
  • rebase 中的衝突是逐 commit 解的：一次 rebase 十個 commit 可能解十次衝突（同一行還會重複遇到）。commit 越零碎、branch 越長壽，rebase 越痛——這又回到「工作切小」。
  • 以為 rebase 會弄丟東西：rebase 前的狀態一直都在 git reflog 裡（30 天起跳）。真的搞砸了：git reset --hard ORIG_HEAD（或 reflog 找到 rebase 前那筆）就回來了。
💡 給你的優化建議 你在 mac 與 Windows 間切換開發，同一條 branch 兩邊輪流推——這正是 git config --global pull.rebase true 的教科書適用情境：從此 git pull 不再產生「Merge branch …」雜訊 commit。 （只影響 pull 的行為，不會動到任何已推送的歷史，對你的 handoff 流程無副作用。）

✅ Takeaways

  • rebase = 換基底重放；歷史變線性，commit 全部換新 hash。
  • 金律：commit 一旦被別人（或別台機器）拿到，就不要再 rebase 它。
  • 改寫過的 branch 用 --force-with-lease 推，永遠不用 --force。
  • 兩機輪替的 branch 用 pull --rebase，避免雜訊合併 commit。
  • 搞砸了有 reflog / ORIG_HEAD 當後悔藥；rebase 不會真的弄丟 commit。
