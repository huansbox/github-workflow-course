trigger

workflow 的 on: 區塊決定它何時醒來。選對事件，自動化才會在對的時機做對的事——以及，不會無限迴圈。

📊 你的數據 workflow_dispatch 在你的紀錄只出現 3 次。醫生的 repo 裡它幾乎無所不在—— 不是因為他愛手動，而是每個自動 workflow 都留一個手動後門，出事時能重跑。 這一課還會解開他 auto-merge 註解裡那個關鍵謎題：為什麼自動合併之後，部署要用 dispatch 顯式接力。

常用觸發事件

事件何時醒來典型用途
pushcommit 進到指定 branch部署、發布——「merge 觸發自動化」的主力
pull_requestPR 開啟/更新時CI 檢查（lint、test）——把關卡掛在合併之前
schedulecron 表達式的時刻每日出刊、定期同步、健檢——醫生的「定期任務」
workflow_dispatch人（或 API）按下執行手動後門、參數化任務
workflow_run另一個 workflow 跑完時接力：CI 完成 → auto-merge
issues / issue_commentissue 開啟/貼 label/留言時label 驅動自動化——醫生的 issue-to-card
releaserelease 發布時發版後的產物建置、通知

過濾器：branches 與 paths

on:
  push:
    branches: [main]          # 只有 main 的 push
    paths:                    # 且改到這些檔案才觸發
      - "src/**"
      - "!docs/**"            # 排除
  schedule:
    - cron: "30 22 * * *"     # UTC 22:30 = 台北 06:30
  workflow_dispatch:
    inputs:
      target:
        description: "要重建的項目（空=全部）"
        required: false

對應指令：gh workflow run deploy.yml -f target=abc、gh run list --workflow=deploy.yml。

三個必知的行為

  • cron 是 UTC：台北時間 (UTC+8) 要自己換算——想要早上 6:30 跑，寫 30 22 * * *。且 schedule 不保證準點，尖峰時段可能延遲數分鐘到數十分鐘；分鐘級精確的任務不要指望它。
  • GITHUB_TOKEN 的遞迴抑制：workflow 裡用預設 token 做的 push、merge 等動作，不會觸發其他 workflow——這是 GitHub 防止「workflow 觸發 workflow」無限迴圈的保護。醫生的 CCChange 就撞上它：auto-merge workflow 合併 PR 產生的 push 不會啟動 deploy.yml，網站會默默停在舊版。他的解法：workflow_dispatch 是文件明載的例外——auto-merge 最後一步用 gh workflow run deploy.yml 顯式接力（這需要 actions: write 權限）。
  • schedule 會被停用：public repo 60 天沒有 commit 活動，排程 workflow 會被自動停用（會發通知信）。長期無人動的 repo 上的 cron 不是永動機。

醫生的觸發選擇學

vox-styled-reels 的 issue-to-card workflow 用 issues: types: [labeled] 而不是 [opened, labeled]——因為「開 issue 時就帶著 label」會同時發出 opened 和 labeled 兩個事件， 兩個一起監聽就會 double-run、在同一條 branch 上打架。labeled 單獨監聽同時涵蓋 「開單即帶 label」與「後來才貼 label」兩種情境。觸發事件的選擇是設計，不是填空。

常見的坑

  • paths 過濾讓 run「完全不出現」：不是跑了被跳過，是根本沒有 run 記錄。設了 paths: 的部署 workflow，改了範圍外的檔案就不部署——忘記這件事會以為 CI 壞了。反過來，該設不設（例如 wiki 發佈 workflow 沒設 paths），高頻 push 的 repo 會空跑不停——你的 repo-wiki skill 文件裡就有這條警告。
  • pull_request 預設只對 opened / synchronize / reopened 反應：想在「PR 被貼 label」「轉出 draft」時觸發要自己加 types。
  • 用 PAT（個人 token）繞過遞迴抑制：可行但危險——迴圈保護沒了，就要自己保證不會 A 觸發 B、B 又觸發 A。能用 dispatch 顯式接力就別繞。
  • 手動後門缺席：純 schedule 的 workflow 失敗後，你只能等下一個週期驗證修復。永遠加一個 workflow_dispatch:（一行而已），除錯時能立刻重跑。

✅ Takeaways

  • CI 掛 pull_request（合併前把關），部署掛 push: branches: [main]（合併後行動）。
  • cron 是 UTC（台北 −8）、不準點、公開 repo 60 天不活動會停用。
  • GITHUB_TOKEN 做的 push/merge 不觸發其他 workflow；接力用 workflow_dispatch 顯式 dispatch。
  • 每個自動 workflow 都加 workflow_dispatch: 手動後門。
  • 觸發事件要挑（labeled vs opened）、過濾器要想（paths 的兩面刃）——這是設計決策。
